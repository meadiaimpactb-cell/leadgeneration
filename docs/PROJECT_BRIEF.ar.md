# برومت التنفيذ الكامل — الموقع المؤسسي B2B لأمد الحرف
### Laravel 11 + Inertia + Vue 3 (SSR) + MySQL/phpMyAdmin — عربي/إنجليزي — تصميم بمستوى Figma

> **كيف تستخدم هذا الملف:** هذا هو المصدر الوحيد للحقيقة (Single Source of Truth) للمشروع. الصقه كاملاً كسياق للوكيل البرمجي (Claude Code / Cursor)، أو ضعه في جذر المستودع باسم `PROJECT_BRIEF.md` وأشر إليه من `CLAUDE.md`. أي طلب لاحق يجب أن يُقاس على هذا الملف. أي بند غير مذكور هنا = خارج النطاق حتى يُعتمد كتابةً.

## 0. الدور والتكليف

أنت **مهندس برمجيات كامل المكدس (Full-Stack) + مصمم واجهات ومنتج**، مكلّف ببناء الموقع الإلكتروني المؤسسي لشركة **أمد الحرف (Amad Craft)** من الصفر، بلا قوالب جاهزة وبلا أنظمة إدارة محتوى جاهزة.

تعمل بمنهجية: **تخطيط → نموذج أولي لصفحة واحدة واعتمادها → بناء → مراجعة ذاتية → تسليم**. لا تكتب الكود قبل اعتماد النموذج الأولي.

**ثلاثة قيود لا تُكسر:**
1. **لا تكتب محتوى تسويقياً ولا رسائل ولا نصوصاً.** كل المحتوى يصل جاهزاً من أمد الحرف. أنت تبني الحاويات (containers) وتترك النص يأتي من لوحة التحكم. المسموح فقط: نصوص واجهة وظيفية (أزرار، تنبيهات، رسائل خطأ) وتُخزَّن في ملفات الترجمة.
2. **لا تبنِ أي وظيفة تجارية.** لا سلة، لا دفع، لا طلبات، لا مخزون، لا لوجستيات، لا فوترة، لا ضرائب، لا عملات.
3. **لا محتوى ثابت داخل الكود (No hardcoded content).** الموقع ديناميكي 100%؛ كل نص وصورة ورقم ورابط وزر يُدار من لوحة التحكم ويُخزَّن في قاعدة البيانات.

## 1. طبيعة المشروع والهدف

**ما هو:** موقع مؤسسي تعريفي (Showcase) موجّه للقطاع المؤسسي B2B، وظيفته إقناع الزائر المؤسسي ثم دفعه للتواصل عبر دعوة اتخاذ إجراء.

**ما ليس هو:** ليس متجراً إلكترونياً، ولا بديلاً عن متجر زد القائم.

**الهدف الوحيد القابل للقياس:**
> **عدد وجودة العملاء المحتملين (Leads) المؤسسيين الواصلين عبر الموقع.**

لا يُقاس البيع من هذا الموقع لأنه لا يتم فيه بيع. كل قرار تصميمي أو تقني يجب أن يُبرَّر بأثره على هذا المؤشر الواحد.

**ما يقدّمه الموقع:**
- عرض خدمات أمد الحرف وتوضيح ما يستفيده العميل منها.
- إبراز التميّز: لماذا أمد الحرف دون غيرها (محتوى تسويقي نصّي يصل جاهزاً).
- عرض المنتجات بشكل تعريفي فقط، دون أي توجيه للشراء المباشر.
- أزرار دعوة اتخاذ إجراء بعبارات محددة، موزّعة داخل المحتوى، تؤدي جميعها إلى **خانة تعبئة بيانات واحدة**.

| 2 | صفحات الحلول للشركات |

| 9 | النسختان العربية والإنجليزية |

### 2.2 خارج النطاق — لا يُنفَّذ إطلاقاً
- سلة الشراء، روابط الدفع، صفحات الدفع.
- اللوجستيات، إدارة المخزون، الشحن.
- الحسابات، الفوترة الضريبية، تعدد العملات.
- طلبات الشراء أو تحديد منتجات وشرائها.
- أي وظيفة من وظائف المتجر الإلكتروني.

### 2.3 ما تم إلغاؤه صراحةً — لا يُبنى (تنبيه للمطوّر: قد ترد في مسودات قديمة)
- ❌ استمارة طلب عرض سعر مؤسسي.
- ❌ الاستمارة الرئيسية، واستمارات التأهيل، واستمارات الحرفيين، واستمارات الشركاء والجهات — **تُستبدل جميعاً بخانة تواصل واحدة**.
- ❌ صفحة «اطلب عرض أسعار» المستقلة.
- ❌ استقبال طلبات عروض الأسعار وشرائح الضمان بصيغتها المفصّلة.
- ❌ القياس الموحّد للمبيعات بين الموقع والمتجر ونسب البيع إلى مصدرها.
- ❌ أي كتابة محتوى أو رسائل تسويقية من جهة التطوير.
- ❌ أي وظيفة تجارية: دفع، سلة، مخزون، لوجستيات، فوترة، عملات.
- ❌ محتوى «الصفحة الخامسة» وخريطة المحتوى — يصل جاهزاً من أمد الحرف.

## 3. الجمهور المستهدف (استهداف مقصود وضيّق، وليس عاماً)

| الفئة | الوصف | الأولوية |
|---|---|---|
| الجهات الحكومية وشبه الحكومية | مثل: الدرعية، نيوم وما شابهها | **الأولى** |
| شركات القطاع الخاص المحددة | فقط الشركات المحددة، وليس كل القطاع الخاص | الثانية |
| الشركاء (Partners) | شركات الفعاليات، المعارض والمؤتمرات، شركات التسويق بالعمولة — جميعها تُعامل كشركات | الثالثة |
| الحرفيون | أربعة أنواع محددة فقط هم المستهدفون، وما عداهم غير مستهدف | الرابعة |

> تحديد هذه الفئات ومحتواها يصل جاهزاً ضمن ملف المحتوى. المطلوب منك: بناء نموذج بيانات `sectors` يستوعب هذه الفئات ديناميكياً، وصفحة قطاع لكل فئة.

## 4. العلاقة بالمتجر الإلكتروني (متجر زد)

المتجر الحالي على منصة زد (`amadcraft.sa`) **يستمر في العمل كما هو، دون أي تغيير في وظائفه أو منتجاته**. الموقع الجديد يعمل بجانبه، لا بديلاً عنه.

**الفصل بين القناتين:**

| | المتجر الإلكتروني (زد) | الموقع المؤسسي (هذا المشروع) |
|---|---|---|
| النموذج | C2B | B2B |
| الجمهور | الأفراد المستهلكون | الشركات، الجهات الحكومية، الجهات المانحة، الحرفيون |
| الغرض | شراء قطعة أو هدية دون تخصيص | عرض القدرات والأثر واستقبال التواصل |
| الدورة | فورية: اختيار منتج ← زر شراء | طويلة: تخصيص + هوية + كميات + عرض فني، قد تستغرق شهرين |

**قواعد الربط الملزمة:**
- يجوز وجود رابط للمتجر داخل صفحات الشركات لمن أراد الانتقال إليه — **دون أي دفع أو توجيه بيعي**. الموقع لا يوجّه الزائر للشراء المباشر.
- المتجر لا يوجّه الزائر المؤسسي إلى صفحة «اطلب عرض سعر» — لا توجد صفحة كهذه أصلاً، بل دعوة اتخاذ إجراء وخانة تواصل فقط.
- **لا يوجد قياس موحّد للمبيعات بين القناتين**، لأن الموقع المؤسسي لا يتم فيه بيع. القياس الوحيد منه: عدد العملاء المحتملين وجودتهم.
- إغلاق المبيعات يتم عبر فريق المبيعات ونظام إدارة علاقات العملاء (المتابعة حالياً عبر Trello).

## 6. آلية جمع العملاء المحتملين — أهم آلية في الموقع

**القاعدة الحاكمة:** أقل عدد ممكن من الخطوات وأقل قدر ممكن من البيانات، حتى لا يهجر العميل المحتمل الموقع، وحمايةً لخصوصية بياناته.

### 6.1 مواصفة النموذج (ملزمة حرفياً)

| الحقل | إلزامي؟ | المواصفة |
|---|---|---|
| وسيلة التواصل | ✅ **الوحيد الإلزامي** | حقل واحد يقبل **بريد إلكتروني أو رقم جوال** — الخيار مفتوح للزائر. الاكتشاف تلقائي (auto-detect) بلا اختيار نوع. |
| رسالة | ❌ اختياري | سطر واحد، يكتب فيه الزائر ما يريد (مثال: «عندي مؤتمر، تواصلوا معي»). |
| الاسم | 🚫 **لا يُطلب** | لا اسم ولا أي بيانات إضافية إطلاقاً. |

- **نموذج واحد فقط** يُستخدم لجميع الفئات: الحرفيون، الشركاء، الجهات الحكومية، القطاع الخاص — دون استمارات منفصلة.
- بقية البيانات يستكملها فريق المبيعات عند التواصل وإغلاق الطلب.
- حماية: Honeypot + Rate limiting + Cloudflare Turnstile (بلا CAPTCHA مرئي مزعج).

### 6.2 ما يحدث بعد الإرسال (السلسلة كاملة)
1. يُسجَّل الطلب في قاعدة بيانات الموقع (`leads`).
2. يُرسَل **فوراً** إلى نظام إدارة علاقات العملاء (CRM) عبر Job في الطابور.
3. يصل تنبيه مباشر لفريق أمد الحرف (بريد + Webhook قابل للتوسّع لـ WhatsApp/Slack).
4. يستلم المرسِل رسالة تأكيد.
5. يُحفظ مع كل طلب **مصدره التسويقي** (UTM كامل + referrer + landing page + gclid/fbclid) لتتبّع التحويلات والأهداف.

### 6.3 معمارية CRM (نقطة تصميمية حرجة)
النظام الحالي هو CRM الخاص بـ **Odoo**. الاتجاه المرجّح هو إلغاؤه والانتقال إلى **CRM منصة زد (Zid)** ليعمل الموقع والمتجر على نظام واحد.

> **لذلك: لا تربط بمزوّد واحد.** ابنِ طبقة تجريد:
> ```php
> interface CrmDriver { public function pushLead(Lead $lead): CrmResult; }
> ```
> بتنفيذات: `OdooCrmDriver`، `ZidCrmDriver`، `WebhookCrmDriver` (احتياطي)، `NullCrmDriver` (بيئة التطوير). يُختار المزوّد من `config/crm.php` + متغير بيئة، وقابل للتبديل **دون تعديل كود**.
> **كحد أدنى: يجب أن يكون الموقع جاهزاً للربط مع Odoo عند الإطلاق.**
> بدون ربط CRM ستصل الطلبات إلى البريد الإلكتروني فقط دون متابعة منظّمة — وهو **غير مقبول**.

سجّل كل محاولة مزامنة في `crm_sync_logs` مع إعادة محاولة تلقائية (exponential backoff) وتنبيه عند الفشل النهائي.

## 7. المعمارية التقنية

### 7.1 المكدّس المعتمد
| الطبقة | التقنية |
|---|---|
| الواجهة الخلفية | **Laravel 11** (PHP 8.3) |
| الواجهة الأمامية | **Vue 3** (Composition API + `<script setup>`) + **Vite** |
| الجسر | **Inertia.js** مع **SSR مفعّل** |
| قاعدة البيانات | **MySQL 8** تُدار عبر **phpMyAdmin** |
| التنسيق | Tailwind CSS + طبقة توكنز CSS مخصصة (RTL-first) |
| الطوابير | Laravel Queue (database أو Redis) + Supervisor |
| البحث/الكاش | Cache: Redis أو file — Cache للصفحات العامة |
| الصلاحيات | `spatie/laravel-permission` |
| الوسائط | `spatie/laravel-medialibrary` + تحويل تلقائي WebP/AVIF |
| السجلات | `spatie/laravel-activitylog` |
| الترجمة | نمط جداول الترجمة (Translation tables) — **لا حزم ترجمة سحرية غامضة** |

### 7.2 لماذا Inertia + SSR وليس SPA منفصلاً (قرار معماري ملزم)
SEO شرط قاطع في هذا المشروع. تطبيق Vue أحادي الصفحة (SPA) يُسلِّم HTML فارغاً لمحركات البحث ويضرّ بالأرشفة. **Inertia مع SSR** يعطيك:
- HTML مكتمل من الخادم لكل صفحة (أرشفة سليمة + سرعة First Contentful Paint).
- تجربة Vue تفاعلية كاملة على العميل.
- روابط `<a>` حقيقية وحالات HTTP صحيحة (200/301/404) — أساسية لـ SEO.
- بساطة: لا حاجة لبناء API منفصل وتوثيقه وتأمينه لكل صفحة.

> بديل مقبول فقط إن تعذّر SSR: Blade كطبقة قشرة (shell) + جزر Vue (Vue Islands) للمكونات التفاعلية. **الممنوع: SPA خالص يعتمد على العميل في التوليد.**

### 7.4 قواعد الكود
- PSR-12 + Laravel Pint. ESLint + Prettier لـ Vue.
- Form Requests لكل إدخال. Policies لكل مورد في لوحة التحكم.
- لا استعلامات N+1 (استخدم `with()` و`Lazy` بحذر) — راقب بـ Laravel Debugbar في التطوير.
- كل نص واجهة عبر `__()` أو `$t()` — **لا نص مكتوب مباشرة في القالب**.
- Migrations قابلة للتراجع (down) دائماً. Seeders لبيانات هيكلية فقط (لا محتوى تسويقي وهمي في الإنتاج).
- اختبارات Feature إلزامية لمسار الـ Lead كاملاً (إرسال → تخزين → CRM → إشعار → تأكيد).

## 9. لوحة التحكم (Admin Panel)

مسار `/admin`. مبنية بنفس المكدّس (Inertia + Vue)، **لا Filament ولا Nova** — لوحة مخصصة كما هو مطلوب، بواجهة عربية RTL افتراضياً.

### 9.1 القدرات الإلزامية
- إضافة وتعديل وحذف **الصفحات والأقسام والمحتوى** دون الحاجة لجهة تقنية.
- **باني أقسام (Section Builder)**: سحب وإفلات لترتيب الأقسام داخل الصفحة، اختيار نوع القسم، تعبئة محتواه بلغتين.
- **إنشاء صفحات حملات تسويقية بسهولة تامة** — نقطة حرجة لأن فريق الحملات هو من سيعمل عليها. Wizard من 3 خطوات: اختر القالب ← عبّئ المحتوى ← انشر.
- إدارة القوائم (Header/Footer) والصور والفيديوهات والملفات.
- **حفظ المسودات والمعاينة قبل النشر** (Preview token برابط سرّي).
- **صلاحيات متدرجة**: `super-admin` (كل شيء) / `editor` (محتوى فقط) / `campaign-manager` (الحملات وصفحات الهبوط) / `sales` (العملاء المحتملون فقط، للقراءة والتصدير وتغيير الحالة).
- **تصدير قائمة العملاء المحتملين في أي وقت** (CSV / XLSX) مع فلاتر بالتاريخ والحملة والحالة والمصدر.
- لوحة قياس داخلية (انظر §12).
- سجل تدقيق: من غيّر ماذا ومتى.
- محرر ثنائي اللغة جنباً إلى جنب (AR | EN) مع مؤشر «الترجمة ناقصة».

### 9.2 قواعد أمان اللوحة
- 2FA اختياري لحسابات المدراء، إلزامي لـ `super-admin`.
- Rate limiting على تسجيل الدخول، قفل بعد 5 محاولات.
- Policies على كل مورد، لا اعتماد على إخفاء الأزرار فقط.

## 10. نظام التصميم UI/UX — بمستوى تسليم Figma

### 10.1 الاتجاه التصميمي (Design Direction)

**الفكرة:** «النسيج المؤسسي». أمد الحرف تحوّل الحرفة إلى منتج مؤسسي — والتصميم يجسّد ذلك: **بنية مؤسسية صارمة (شبكة، هدوء، ثقة) يخترقها خيط حِرفي واحد**.

**العنصر التوقيعي (Signature):** **خيط السدو** — شريط نسيج رفيع (SVG hairline pattern) مستوحى من نقوش السدو، يظهر في ثلاثة مواضع فقط:
1. فاصل بين الأقسام (بديل الخط الرمادي التقليدي).
2. أرضية خفيفة جداً خلف قسم الأثر (الأرقام).
3. تسطير الروابط والأزرار الثانوية عند التمرير — ينسج نفسه من اليمين لليسار بحركة 300ms.

> لا تكرره في مكان رابع. الجرأة تُنفق في مكان واحد؛ ما حوله يبقى هادئاً ومنضبطاً.

**ما نتجنبه صراحةً:** الخلفية الكريمية الفاتحة مع سيريف عالي التباين ولون طيني (النمط الافتراضي المتكرر)، والتدرجات اللونية الزخرفية، والأيقونات العائمة، والبطاقات الزجاجية (glassmorphism).

### 10.7 الحركة (Motion)
- المنحنى: `cubic-bezier(.2,.7,.3,1)`. المدد: micro `160ms` / عناصر `300ms` / كشف عند التمرير `450ms`.
- كشف الأقسام: `opacity 0→1` + `translateY 16px→0`، مرة واحدة فقط، بتأخير متتابع 60ms للعناصر داخل الشبكة.
- عدّاد أرقام الأثر: يعدّ مرة واحدة عند الظهور، خلال 900ms.
- **`prefers-reduced-motion: reduce` يلغي كل ما سبق** ويُبقي الحالة النهائية.

### 10.8 الوصول (Accessibility) — WCAG 2.2 AA
- تباين نص/خلفية ≥ 4.5:1 (≥ 3:1 للنص الكبير والأيقونات الوظيفية).
- `:focus-visible` مرئي دائماً: إطار 2px `--lavender-700` + إزاحة 2px. لا `outline: none` بلا بديل.
- تنقّل كامل بلوحة المفاتيح، ترتيب منطقي، رابط «تخطَّ إلى المحتوى».
- HTML دلالي: `<header> <nav> <main> <section> <footer>`، عنوان `<h1>` واحد لكل صفحة، تسلسل رؤوس صحيح.
- كل صورة لها `alt` يُدار من لوحة التحكم (`media_translations`). الصور الزخرفية `alt=""`.
- الفيديو: تحكّم يدوي، بلا تشغيل تلقائي بصوت.
- أهداف اللمس ≥ 44×44px.

## 12. تعدد اللغات (i18n)

- اللغتان: **العربية والإنجليزية فقط**.
- **النسخة الإنجليزية ضرورية جداً وليست ثانوية** — كثير من القطاعات المستهدفة، خصوصاً الجهات شبه الحكومية، لا يتحدث العاملون فيها العربية.
- البنية: بادئة لغة في المسار `/ar/...` و`/en/...`، مع تحويل من الجذر حسب `Accept-Language` وحفظ التفضيل في كوكي.
- `<html lang="ar" dir="rtl">` ⇄ `<html lang="en" dir="ltr">` — يتبدّل تلقائياً.
- **RTL-first**: استخدم الخصائص المنطقية حصراً (`margin-inline-start`، `padding-inline`، `inset-inline`) — لا `left/right` في CSS.
- الأيقونات الاتجاهية (أسهم، chevrons) تنعكس؛ الشعارات والصور والأرقام لا تنعكس.
- `hreflang` متبادل بين النسختين + `x-default`.
- نصوص الواجهة في `resources/lang/{ar,en}`؛ محتوى الموقع في جداول الترجمة.
- سلوك النقص: إن غابت ترجمة إنجليزية لصفحة، **لا تعرض عربية بدلاً منها** — أخفِ الصفحة من النسخة الإنجليزية ومن sitemap الإنجليزي، وأظهر تنبيهاً في لوحة التحكم.

> ⚠️ **قرار مطلوب من الإدارة:** هل تُطلق النسخة الإنجليزية في المرحلة الثانية أم مع الإطلاق الأول؟ ابنِ البنية جاهزة للحالتين، واجعل تفعيل النسخة الإنجليزية مفتاحاً في `settings`.

## 13. تحسين محركات البحث (SEO)

يُسلَّم الموقع مهيّأ تقنياً بالكامل:
- بنية عناوين وروابط صحيحة وصديقة لمحركات البحث (slugs عربية مرمّزة بشكل سليم).
- `Meta Title` و`Meta Description` **قابلة للتحرير لكل صفحة ولكل لغة** من لوحة التحكم.
- خريطة موقع `sitemap.xml` **تُحدَّث تلقائياً** (index + خرائط فرعية لكل لغة).
- `robots.txt` قابل للإدارة.
- Schema.org المناسبة: `Organization`, `WebSite`, `BreadcrumbList`, `Service`, `FAQPage`, `Article` للقصص.
- صور محسّنة: WebP/AVIF، `srcset`، `width/height` صريحان، `loading="lazy"` عدا الهيرو، `fetchpriority="high"` للهيرو.
- سرعة تحميل عالية (انظر §14).
- Canonical لكل صفحة + `hreflang`.
- **جدول `redirects`** لإدارة التحويلات 301 من لوحة التحكم — ضروري لحماية أرشفة الروابط القديمة.
- معالجة الأخطاء التقنية المؤثرة على الأرشفة: 404 صحيحة، لا سلاسل تحويل، لا محتوى مكرر.
- **يُستعان بمختص SEO** لبناء الموقع على الكلمات المفتاحية التي يبحث بها الجمهور المستهدف فعلياً — تصل قائمة الكلمات كمدخل، وتُطبَّق في العناوين والأوصاف وبنية الصفحات.

> لا يشمل ذلك ضمان تحقيق ترتيب معيّن في نتائج البحث.

### 15.2 معايير الجودة
- سرعة تحميل عالية — **ضرورية جداً**.

### 15.3 الأمان
- HTTPS إجباري + HSTS + شهادة SSL مفعّلة.

- لا أسرار في المستودع — `.env` فقط، مع `.env.example` كامل.
- سجل تدقيق لكل تعديل إداري.

## 16. النطاق والاستضافة والنشر

- ربط الموقع بالنطاق والاستضافة وتفعيله بالكامل.
- خيار مطروح: نقل المتجر إلى عنوان فرعي تحت النطاق نفسه، وتخصيص نطاق فرعي (Sub-domain) للموقع المؤسسي B2B.
- **شرط قاطع:** ألّا يؤثر ذلك على تحسين محركات البحث (SEO) المبني خلال السنوات الماضية.
- **إذا كان النقل سيؤثر على SEO فلا يُنفَّذ إطلاقاً**، ويبقى المتجر على نطاقه، ويُخصَّص نطاق فرعي للموقع المؤسسي. القرار التقني متروك للجهة المنفّذة، والشرط هو **حماية SEO**.
- في جميع الأحوال: لا يتوقف المتجر، ولا تتوقف طريقة إدارته، ولا تُفقد أي بيانات أو طلبات، ويجب **تحويل تلقائي (301) لكل الروابط الحالية دون انقطاع**.

**بيئات:** `local` → `staging` (محمي بكلمة مرور + `noindex`) → `production`.
**النشر:** Git + خط أنابيب (deploy script/CI): `composer install --no-dev` ← `npm ci && npm run build` ← `php artisan migrate --force` ← بناء SSR ← `optimize` ← إعادة تشغيل الطوابير و SSR.

## 22. قيود صارمة على الوكيل البرمجي (اقرأها قبل كل جلسة)

1. **لا تخترع محتوى.** إن نقص نص، ضع `placeholder` واضحاً في لوحة التحكم وأبلغ — لا تكتب نسخة تسويقية.
2. **لا تضف ميزة غير مذكورة هنا.** إن رأيت ضرورة، اقترحها ولا تنفّذها.
3. **لا تبنِ أي وظيفة تجارية** (§2.2) مهما بدت منطقية.
4. **لا تستخدم قوالب جاهزة أو أنظمة إدارة محتوى** — واجهات مبرمجة من الصفر بمكونات Vue وفق الهوية المعتمدة.
5. **لا تضع نصاً مباشرة في القوالب** — كل شيء عبر الترجمة أو قاعدة البيانات.
6. **لا تستخدم `left/right` في CSS** — الخصائص المنطقية فقط (RTL-first).
7. **لا تكسر أرشفة الروابط القديمة** — أي تغيير مسار يمرّ عبر جدول `redirects`.
8. **لا تربط بمزوّد CRM واحد مباشرة** — عبر طبقة التجريد فقط.
9. **لا تضع مفاتيح أو معرفات تتبّع في الكود** — في `settings` أو `.env`.
10. عند أي غموض: **اسأل قبل أن تبني.** كل نقطة غير واضحة تُطرح للنقاش قبل بدء التنفيذ.
